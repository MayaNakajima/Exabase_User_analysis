# 引き継ぎ書 — エクサベースAI 利用実態分析

最終更新: 2026-07-31

このドキュメントは、本分析を**別の担当者が再実行・月次更新できる**ようにするための手順書。
指標の定義や設計思想は `仕様書.md` を参照。

## 1. 全体像

生ログ(xlsx) を入力に、7ステップのPythonスクリプトで
Excel集計ブックとHTMLダッシュボードを生成する。STEP3のAI分類のみ手動介在が必要。

```
gai-export-*.xlsx
   │ 01_extract           会話単位に集約
   ▼ conversations.json
   │ 02_classify_prep     AI分類用チャンク生成
   ▼ chunks/chunk_*.json
   │ 【AI分類：手動/サブエージェント】  ← ここだけ人手
   ▼ chunks/result_*.json
   │ 03_merge_classification  統合・検証
   ▼ classification.json
   │ 04_analyze           リテラシースコア + 4象限
   ▼ user_rows.json, meta.json
   │ 05_aggregate         各種クロス集計
   ▼ aggregates.json
   │ 06_build_xlsx / 07_build_dashboard
   ▼ output/*.xlsx, output/*.html
```

## 2. 環境準備

```bash
pip install -r requirements.txt      # openpyxl
```

- Python 3.9+ を想定（標準ライブラリ + openpyxl のみ）。
- Excelの数式検証をする場合のみ LibreOffice（`soffice`）が必要。数式は合計4つだけなので必須ではない。

## 3. 月次更新の手順

1. エクサベースAI管理画面から対象月のログをエクスポートし、
   `data/gai-export-YYYY_MM_DD-YYYY_MM_DD.xlsx` として保存。
   （`01_extract.py` は `data/` 内の `gai-export-*.xlsx` の**最新（名前順で末尾）**を自動選択）

2. STEP1・2 を実行。
   ```bash
   cd scripts
   python 01_extract.py
   python 02_classify_prep.py
   ```

3. **AI分類（手動介在）**。`data/chunks/chunk_0.json`〜`chunk_9.json` を AI に渡し、
   `scripts/classification_prompt.md` のプロンプトで12カテゴリに分類させ、
   結果を `data/chunks/result_0.json`〜`result_9.json` として保存する。
   - Cowork/Claude 上では、10チャンクを**並列サブエージェント**に投げるのが速い（初回はこの方法で実施）。
   - 手作業でも可。出力はフラット辞書 `{"会話ID":"C0X", ...}` を推奨（リスト形式でもSTEP3が吸収）。
   - **全件必須**。欠落は STEP3 が C12 で補完し警告する。

4. STEP3〜7 を実行。
   ```bash
   python 03_merge_classification.py   # 「未分類:0」を確認
   python 04_analyze.py                # 中央値・象限・相関を確認
   python 05_aggregate.py
   python 06_build_xlsx.py
   python 07_build_dashboard.py
   ```

5. `output/` の xlsx / html を確認。ファイル名の年月は必要に応じて手動で調整
   （現状 `..._202607...` 固定。月を変える場合は `06`/`07` の出力ファイル名を編集）。

## 4. 検証（推奨）

- **整合性**: STEP3で「未分類:0 / 余分:0 / 不正コード:0」。会話数・ユーザー数が
  STEP1の出力と一致すること。カテゴリ/パートナー/象限の各会話数合計が総会話数に一致すること。
- **Excel数式**: LibreOfficeがあれば再計算しエラー0を確認。
  ```bash
  soffice --headless --convert-to xlsx --calc output/*.xlsx   # もしくは既存recalcスクリプト
  ```
  （合計行の SUM のみ。値はスクリプトが算出済み）
- **ダッシュボード**: ブラウザで開き、全グラフとテーブルが表示されるか確認。
  埋め込みJSONは `const D={...}`。`DATA_PLACEHOLDER` が残っていないこと。

## 5. カスタマイズ箇所

すべて `scripts/config.py` に集約:

- `CAT_NAMES` … 12分類の定義（変更時は `classification_prompt.md` も要同期）
- `ADV_TOOLS` … 高度ツールの集合（**唯一の定義元**。14/15 はここを import。新ツール追加時はここへ）。
  画像生成(高速/高性能)は 2026-08 に除外済み（将来チャット内容ベースで高度分類する余地あり。詳細は評価仕様§4）。
- `LITERACY_WEIGHTS` … リテラシースコアの重み（合計1.0を維持）
- `SIMPLE_CATS` / `OVERSPEC_MAX_TURNS` … 過剰スペック候補の判定条件

象限の分割は中央値ベース（`04_analyze.py`）。固定閾値にしたい場合はここを変更。

## 6. よくあるハマりどころ

- **モデル階層が Unknown になる**: パートナー文字列の書式が変わった可能性。
  `01_extract.py: tier()` の正規表現 `/\s*(Economy|Standard|Premium)` を確認。
- **新しいツール名が高度ツール判定に入らない**: `config.py: ADV_TOOLS` に追記。
- **ツール名が途中で切れて集計される**（例「画像生成 (高速」「Nano Banana)」）: ツール名自体が括弧内にカンマを
  含むため。`10_ingest.py: split_tools()` が括弧の外のカンマだけで分割する（素朴な `split(",")` に戻さないこと）。
- **result_*.json の形式ゆれ**: フラット辞書／リストの両方をSTEP3が吸収するが、
  値がカテゴリコード（`C01`〜`C12`）であること。想定外コードは STEP3 が不正としてカウント。
- **ダッシュボードのカテゴリグラフが出ない**: テンプレートは `D.agg.cat || D.agg.cats` の
  両対応。テンプレートを差し替える際はこのフォールバックを壊さないこと。
- **文字化け**: すべて UTF-8 で読み書き。Windowsで開く際のエンコーディングに注意。

## 7. データの取り扱い（重要）

- `data/`（生ログ・中間ファイル）と `output/`（成果物）は
  **社員メールアドレス・チャット本文・チャット抜粋**を含む。
- `.gitignore` で `data/` と **`output/` はいずれも除外**（成果物も社員名・抜粋を含むため）。
  データ・成果物は**実行用 Box フォルダ**で共有する（README「Box 運用」）。リポジトリは Private 維持。
- 外部共有時は社員名（メールのローカル部）の匿名化を検討。
- 作業はブランチを切り `docs/変更履歴.md` に記録。コミットは GitHub アプリ、レビュー後 main へマージ。

## 8. 今後の拡張候補

- 会話全体（初回発話だけでなく全ターン）を使った高精度分類。
- 月次トレンド（複数月を並べた推移）。`aggregates.json` に月キーを追加して蓄積。
- 部署マスタを結合した部署別分析。
- 「有用だった会話（評価列）」の活用—現状 評価列はほぼ空だが将来値が入れば満足度分析が可能。

# 【全期間・月次版】運用手順（現行）

単月版(01〜07)を全期間・月次に拡張した現行パイプライン（10〜17 + build_archive）。

## 1. 全体像
```
data/raw_exports/ に 月次xlsx(全パート) + メンバー一覧
   10_ingest            → data/conversations_all.json（重複排除・月付与）
   11_members           → data/members.json（グループ/在籍/Claude）
   12_classify_prep     → data/chunks2/c*.json（ユニーク初回発話・30分割）+ uid_map.json
   【AI分類：手動/サブエージェント】 → data/chunks2/r*.json（uid→カテゴリ）
   13_merge_classification → data/classification_all.json（全会話へ展開）
   14_analyze           → data/user_all.json, meta_all.json（稼働月正規化・4象限）
   15_aggregate         → data/aggregates_all.json（月次・グループ×象限・過剰スペック）
   18_employee_master   → data/employee_master.json（社員一覧CSVをメール突合した氏名マスタ）
   16_build_xlsx / 17_build_dashboard → output/..._全期間.xlsx / _ダッシュボード_全期間.html
   build_archive        → data/archive/messages_YYYY-MM.jsonl.gz（保持マスタ・任意）
   19_snapshot          → data/snapshots/snapshot_<最新月>/（16/17の入力4点を保存・任意｜§5.1）
```

- **成果物の月次推移グラフ**：Excelは `月次_用途別／月次_パートナー別／月次_ツール別`（表＋積み上げ棒グラフ）を含む全**14シート**。
  ダッシュボード④は用途/パートナー/ツールの**月次推移スタック棒（実数⇔構成比％切替）**を搭載（`15_aggregate` の
  `usage_trend`／`partner_trend`／`tool_trend` を使用）。

### 氏名突合（STEP18）と成果物への反映
- **社員一覧CSV**（人事、Shift-JIS）を `data/raw_exports/社員一覧*.csv` として配置し、`python 18_employee_master.py` を実行。
  メールアドレスで突合する氏名マスタ `data/employee_master.json`（氏名・カナ・部署・役職）を生成する。
- `16_build_xlsx.py` / `17_build_dashboard.py` はこのマスタをメールで突合し、**氏名・部署**を表示に反映する
  （マスタが無くても既存氏名/メールでフォールバック動作する）。よって **18 → 16 → 17 の順**で実行する。
- ダッシュボードには「各グラフの見方・示唆」「リテラシー向上ガイド」「氏名/カナ/メール/部署での検索」を搭載
  （詳細は仕様書 §H）。テンプレートは `dashboard_all_template.html`。
- 月次更新時は最新年の社員一覧CSVを差し替えて 18 を再実行すれば氏名が更新される。列位置は
  ヘッダー名で自動マッピングするため、年によるレイアウト差は許容される。

### 評価バイアス補正と評価仕様
- リテラシー指標には**手戻り除外**（`config.REWORK_PAT`）と**テンプレ由来の水増し除外**（`config.TEMPLATE_MIN_USERS`）の
  補正が入る（`10_ingest.py`／`14_analyze.py`）。算式・判定・限界の詳細は **`docs/評価仕様.md`**。
- **（解決済み）データ破損対応**：一時 `gai-export-2026_07_01-2026_07_31.xlsx` が破損（zip中央ディレクトリ消失）
  で `10_ingest.py` が読めなかったが、**正常ファイルを再取得**して `data/raw_exports/` に置き直し、
  `10_ingest.py`→`14`→`15`→`16`→`17` を通し直した。7月の手戻り補正も反映済み（全期間 手戻り 5,623件、
  会話数29,548・分類カバレッジ100%は不変）。同種の破損時は正常ファイルを再取得して全期間を再取り込みすること。

## 2. 月次更新の手順
1. 対象月のエクスポートを `data/raw_exports/` に置く。**エクスポートは3万行で分割される**ため、
   期間が長いと part-2, part-3… に分かれる。**全パートを漏れなく揃える**こと（欠けると当該月が
   過少計上され、トレンドを誤らせる。10_ingest の月次件数出力で不連続がないか必ず確認）。
2. 最新のメンバー一覧 `gai-members-export-*.xlsx` も `data/raw_exports/` に更新配置。
3. `python 10_ingest.py`（月次件数の連続性を確認）→ `python 11_members.py`。
4. `python 12_classify_prep.py` → `data/chunks2/c*.json` を **未分類分だけ**AI分類し `r*.json` を保存。
   - 既存月を再分類する必要はない。増えたユニーク発話のみ対象にすればよい（uidは再採番される点に注意。
     厳密な差分運用をしたい場合は、前回の `classification_all.json` を保持し新規会話IDのみ分類する運用に変更）。
   - 本分析では 30チャンク×10並列サブエージェントを3波で実施。プロンプトは `scripts/classification_prompt.md`。
5. `python 13_merge_classification.py`（covered=全会話 を確認）→ `14`→`15`→`18`→`16`→`17`。
   - `18_employee_master.py` は社員一覧CSV（`data/raw_exports/社員一覧*.csv`）から氏名マスタを作る。
     氏名を最新化する場合は最新年のCSVを配置して 18 を再実行（16/17の前に実行すること）。
6. 保持アーカイブを更新: `python build_archive.py`（新規メッセージのみ追記される）。
7. （任意・引き継ぎ用）処理済みスナップショットを保存: `python 19_snapshot.py --zip`。
   生データを集め直さず成果物を再生成できる中間データ一式（`aggregates_all/user_all/meta_all/employee_master`）を
   `data/snapshots/` に保存（Box共有用zipも生成）。受領側は `python 19_snapshot.py --restore <zip>` → `16` → `17` で
   保存時点と同一の Excel/ダッシュボードを再生成できる（重い 10〜15 の再実行不要）。詳細は仕様書 §G.1。

## 3. Claude併用者・グループの管理
- Claude（Claude Code含む）併用者は `config.py: CLAUDE_USERS` で管理。増減時はここを更新。
  過剰スペック集計から除外され、ダッシュボード/Excelで注記される。
- グループ（コア/ライト/ユーザー）は **`21_grouping.py` が算定**し、`members.json`/`user_all.json` の
  `group` に書き戻して 15/16/17 へ反映する（2026-09 統合。旧: メンバー一覧のタグから判定していた）。
  判定ルールは下記「グループ分け統合・自動更新」節と `docs/グループ分け仕様.md` を参照。

## 4. 検証（推奨）
- 10_ingest の月次件数に不連続・急減がないか（＝パート欠落の検知）。
- 13 で covered = 全会話。14 の象限合計 = 利用者数。15 の各集計合計 = 総会話数。
- 17 出力後、ブラウザで全グラフ表示を確認（埋め込みJSONに `DATA_PLACEHOLDER` が残っていないこと）。
- 参考: 本リポジトリではダッシュボードJSをNodeでモック実行し、全チャート生成をスモークテスト済み。

## 5. データ保持（リテンション）
- **正本** = `data/raw_exports/` の原本xlsx（完全・authoritative）。将来分もここへ追加。
- **正規化マスタ** = `data/archive/messages_YYYY-MM.jsonl.gz`（全文・重複排除・月別gzip）。
  `build_archive.py` が原本から生成・追記。検索/再分析はここから。
- どちらも `data/` 配下で **Git対象外**。社員情報を含むためリポジトリは Private 厳守。

# 【グループ分け統合・自動更新】運用手順（2026-09〜）

旧 `AI_User_Group`（Streamlit）を本ツールへ統合し、グループ分けを分析ツールで実施する単一ツール化。
判定ルールの定義は [`グループ分け仕様.md`](グループ分け仕様.md)。ここでは**運用（使い方）**を示す。

## 1. 追加スクリプト
```
grouping_lib.py        … 受験台帳＋複数回判定＋エンゲージメント配分＋取込CSV＋出欠（純関数・副作用なし）
20_exam_ledger.py      … AI資格試験CSV → data/exam_ledger.csv（追記型・複数回受験）
21_grouping.py         … グループ分け → data/grouping_all.json / output/グループ分け結果.xlsx
                          （+ group を members.json/user_all.json へ書き戻し、--snapshot 指定で import.csv 生成）
22_event_attendance.py … 社内イベント出欠(attendance.db)をemail突合 → data/event_metrics.json
update_monthly.py      … 月次フル更新の一括実行（下記2）
update_exam.py         … 試験結果を随時反映（下記3）
classify_chunks.py     … （任意）新規分類を Claude API(Haiku4.5)で自動化（要 ANTHROPIC_API_KEY）
```
パイプライン順序: `10 → 11 → 12 →(分類)→ 13 → 14 → 22 → 21 → 15 → 18 → 16 → 17`。

## 2. 月次更新（前月ログ＋ユーザー一覧をアップロード）
1. `data/raw_exports/` に、前月の利用情報 `gai-export-*.xlsx`（**全パート**）と最新メンバーエクスポート
   `gai-members-export-*.xlsx` を配置（社員一覧CSVも最新化する場合は差し替え）。
2. 実行：
   ```bash
   cd scripts
   python update_monthly.py
   ```
   - 入力が揃っていないと**プリフライトで停止**し不足を表示する。
   - **分類ゲート**：新規プロンプトが0件なら全自動。新規があれば `data/chunks2/c*.json` を生成して停止する。
     - Claude Code 上で `c*.json` を `classification_prompt.md` に従い分類し `r*.json` を保存 → `python update_monthly.py --resume`。
     - または `python update_monthly.py --api`（Claude APIで自動分類）。
   - 完走で `output/` に Excel・ダッシュボード・`グループ分け結果.xlsx`・`import.csv` が更新される。
   - 高度AI分析（分類）は**更新時にフル実行**（増分キャッシュ式・精度維持）。

## 3. 試験結果の反映（随時）
生成AIパスポート試験の結果CSVが出たら、任意のタイミングで：
```bash
cd scripts
python update_exam.py <試験結果CSV>            # 例: ../data/3_AI資格試験情報_*.csv
python update_exam.py <試験結果CSV> --snapshot <取込用CSV/メンバーエクスポート>  # import.csv も生成する場合
```
- 受験台帳 `data/exam_ledger.csv` に**追記**（同一回次×emailは最新で置換）。回次はファイル名の `YYYYMMDD`
  を自動採用（`--date YYYYMMDD` で明示可）。
- 台帳から**最新回優先**で合否を判定し、グループ分け・ダッシュボードを再生成する（利用ログの再取込・AI分類は不要＝軽量）。
- **合否混在は最新回で決定／未受験は結果とみなさない（過去合格＋直近未受験＝合格維持）／管理者6名は自動コア**。

## 4. 管理ツール取込CSV（`output/import.csv`）
グループ分け結果を管理ツールへ反映する一括登録CSV。取込前に `action` の内訳（update/skip/create）を確認する。
`update_monthly.py` は最新メンバーエクスポートをスナップショットに自動生成。単体では `python 21_grouping.py --snapshot <...>`。

## 5. 閲覧（Python不要・ダブルクリック）
- `ダッシュボードを開く.cmd` … 最新の利用分析ダッシュボードHTMLを**既定ブラウザで描画表示**。
- `グループ分け結果を開く.cmd` … 最新の `グループ分け結果.xlsx` を開く。
- 実装補足：`.cmd` 本体はASCII固定（cmdのcp932誤読回避）、日本語処理と起動は `open_*.ps1`（UTF-8 BOM）。
  `.html` の関連付けがエディタでも、既定ブラウザ実行ファイルに `file://` URL を渡して**必ずブラウザで描画**する。
  グラフはChart.jsをCDN参照するため描画時に社内ネット接続が必要。

## 6. 設定（`config.py` / `grouping_lib.py`）
- `ADMIN_USERS`（自動コアの管理者6名）／`ADMIN_SUBGROUPS`／`ADMIN_BY_OWNER`／`EVENT_DB`（出欠DBパス）… `config.py`。
- `EXAM_SCORE`／`DEFAULT_ALLOCATION`／`ENGAGE_WEIGHTS`（利用頻度0.5＋リテラシー0.5）… `grouping_lib.py`。

## 7. 検証（推奨）
- `21_grouping` 出力: 「コア＝管理者＋ランキング」「ランキングコアは全員合格」を確認。総数＝メンバー数。
- `import.csv`: 「管理タグ不一致0」「管理者の権限admin＝人数分」を確認。
- 出欠: グループ×出欠クロス（`グループ分け結果.xlsx` の「イベント出欠×グループ」シート）を確認。
- 閲覧: `.cmd` でダッシュボードがブラウザで**描画**表示される（ソース表示にならない）こと。

# 【現行】Git運用（チャット / Claude Code での git 開発）

このリポジトリは **Claude（チャット / Claude Code）から直接 git 操作**して開発する。
push だけは GitHub 認証が無いため行わず、**push はお手元（GitHub Desktop 等）**で実施する。
branch / commit / merge はチャットから実行できる（下記の対処が前提）。

## マウントの制約と対処（最重要）
- この作業フォルダは Windows フォルダのマウントで、**rename（改名）は可・unlink（削除）は不可**。
- そのため git は commit / merge 自体は正常に行えるが、**処理後に残る `*.lock`（`index.lock`, `HEAD.lock` 等）を
  git が削除できず**、次の git コマンドが「`index.lock: File exists`」で停止する。これが「コミットできない」真因だった
  （他リポジトリも同根。たまたまロックが残っていない時に成功していただけ）。
- **対処：各 git 実行の前に、残留 `*.lock` を退避（rename）する。** 付属ラッパー `tools/gitsafe.sh` が自動で行う。

## 使い方（gitsafe ラッパー）
通常の `git` の代わりに `bash tools/gitsafe.sh` を使う（実行前に残留ロックを退避してから git を実行）。
```bash
bash tools/gitsafe.sh add -A
bash tools/gitsafe.sh commit -m "feat: 概要" -m "- 変更点1" -m "- 変更点2"
bash tools/gitsafe.sh switch -c feature/xxxx
bash tools/gitsafe.sh merge --no-ff feature/xxxx -m "Merge feature/xxxx: 概要"
bash tools/gitsafe.sh log --oneline
bash tools/gitsafe.sh status
```
- 退避ロックは `.git/_locktrash/` に溜まる（unlink 不可のため消せないが**無害**）。気になれば **Windows 側**で `.git/_locktrash` を削除。
- 自動 gc / メンテは stuck lock の発生源なので無効化済み（`gc.auto=0` / `maintenance.auto=false`）。

## 開発フロー（ブランチ運用）
- `main` へ直接ではなく、作業ごとにブランチ（`feature/` `fix/` `docs/` `refactor/`）を切る。
- コミットメッセージに作業内容を残す。**マージ前にレビュー（一旦停止）→ 承認後に `--no-ff` で main へマージ**。
- 変更内容・レビュー観点は `docs/変更履歴.md` に記録。
- **push は Claude では行わない**（認証不可）。push はお手元（GitHub Desktop）。
  remote: `https://github.com/MayaNakajima/Exabase_User_analysis.git`。

## 避ける操作
- `git branch -D`（ブランチ削除）や `git gc` は unlink を多用し stuck lock を残しやすい。
  不要ブランチの削除は GitHub 側かお手元で。実行する場合も gitsafe が次操作前にロックを退避する。
